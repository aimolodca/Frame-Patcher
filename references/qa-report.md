# Отчёт проверки · 1.1

Использовать один формат во всей связке; показывать кратко, сохранять существенные свидетельства. Читать при проверке/передаче результата. ОТК не принимает финал за человека и не запускает ремонт.

## Идентификация

`item_number`, `artifact_version`, `artifact_path_or_id`, `brief_version`, `stage` (`flat`, `screen`, `assets`, `final`, `cover`, по задаче), `reviewer`, `independent` (true только при отдельном проверяющем), принятые исключения и источники эталонов.

## Покрытие и критерии

В `coverage` всегда различать `frames`, `motion`, `audio`, `technical`. Каждая область содержит `status`, `method`, `evidence` и при необходимости `limitations`. Те же статусы применять в списке `checks`: `criterion`, `location_or_time`, `status`, `evidence`, `impact`.

| Статус | Значение |
|---|---|
| `passed` | Требование действительно проверено и выполнено |
| `failed` | Есть наблюдаемый дефект с нарушенным требованием |
| `not_checked` | Проверка не выполнялась |
| `unverifiable` | По доступному материалу вывод невозможен: например буквы неразличимы |
| `not_applicable` | Требование неприменимо, указать почему |

Не превращать `unverifiable` в `passed` или доказанный дефект. Для старых отчётов сохранить исходные обозначения и смысл; при передаче добавить явное соответствие, не переписывать историю. Сетка кадров закрывает только заявленную выборку `frames`; движение требует фактического воспроизведения, звук — прослушивания. Хеши, метаданные и транскрипт не доказывают движение/интонацию/синхронность. Смотреть целиком и крупно рискованные области; технические параметры читать из файла.

В `checks` включать применимые точные тексты, продукт, количество, анатомию/контакты, геометрию, историю и подачу. Для обложки — реальный крючок ролика, иерархию в маленьком превью и каждый заказанный кроп; известные перекрытия интерфейса проверять отдельно. Брендовые каноны и форматные критерии брать из переданного профиля/ТЗ, не из общих вкусов.

Для товарной карточки выделять отдельные применимые `checks`: материал; форма/конструкция; цвет; функция; hero; каждая миниатюра и картинка продавца; точные надписи; `ui_data`. Верный силуэт/цвет не закрывает материал, хороший hero не закрывает галерею. Для экранного результата отдельно записывать геометрию/сохранность страницы, техническую целостность обработки и фотографичность; успех маски, хешей или муара не заменяет визуальный вердикт. Для чистого 2D экранная фотографичность — `not_applicable`.

Привязать отчёт к фактическому `artifact_id`/хешу и при сравнении указать исходный мастер/версию. Сохранять незакрытые обязательные дефекты источника для ведущего; следующий этап не закрывает их обещанием исправления. Исправленный файл требует проверки затронутых критериев; прежний QA остаётся историей.

## Итог

`summary`: `passed`, `failed` или `partial`. `partial` применять только к сводному итогу, не к строке `checks` или области `coverage`: смешанный пункт разделить на проверенную часть и конкретную непроверенную с одним из пяти статусов выше. Любой обязательный дефект даёт `failed`; без дефектов, но с применимыми `not_checked`/`unverifiable` — `partial`. Полный `passed` допустим только при проверке всех обязательных пунктов; он не является `accepted`. Неприменимые области не мешают завершению. Явная человеческая приёмка с раскрытыми ограничениями разрешает уже порученную сдачу; ограничения сохранить.

Дефект описывать: место → наблюдение → нарушенное требование → влияние → адресное предложение. Вкусовые рекомендации отделять. Вернуть отчёт ведущему, не менять его журнал самостоятельно. При самостоятельном исполнении честно назвать самопроверку, не независимый ОТК. Для Frame Patcher дополнительно сохранить `technical_pass`, `visual_acceptance`, `delivery_allowed`; выход процесса 0 сам по себе не разрешает выдачу.
